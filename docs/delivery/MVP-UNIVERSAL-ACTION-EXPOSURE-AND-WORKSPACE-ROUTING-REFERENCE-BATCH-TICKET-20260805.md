## Customer outcome

After login, every person remains a normal Personal user and can use the
MoolSocial customer app without first declaring a profession or creating a
workspace. The Mool launcher exposes only the exact MVP actions that have a
truthful destination. When a person intentionally opens **Workspace**, the app
reopens an existing exact workspace or progressively presents only workspace
types that an authorized launch configuration has published for that person
and geography.

The person sees an attractive, truthful preview followed by complete scope,
eligibility, documents, geography, charges, capabilities and exclusions before
requesting a workspace. A visible card, local selection or successful form
submission never grants a shop, pharmacy, doctor, salon, restaurant, delivery,
Ride, Work, wholesale or creator capability.

## MVP classification

Parent classification: `mvp_required`.

Reason:

- the exact protected OPPO APK still promises Tiffin, Get It Done, standalone
  Pay and universal Work Delivery/Onboard/Verify although the founder postponed

## Journey 1 — normal Personal user after login

1. The person completes the locked sign-in journey.
2. Universal opens in the preserved normal Personal-user context.
3. No modal asks the person to choose a profession, business or workspace.
4. Mool shows only Social, Buy, Eat, Ride, Book and Work; Chat remains global.
5. The person may browse or use an eligible customer journey immediately.
6. If an action projection is loading, its previous safe context remains and a
   bounded loading state is shown; the app does not fall back to the old rail.
7. If an action is unavailable for the current geography or dependency, the UI
   either hides it according to published policy or shows a truthful deliberate
   preview with no live-action claim. It never opens review data as success.
8. Back, app switch, process death and authenticated relaunch restore the last
   safe permitted context. A removed route cannot reappear from saved local
   navigation.

## Journey 2 — exact main-action and sub-action taps

1. Personal user taps **Mool**.
2. Mool reveals the six MVP main actions; standalone Pay is absent.
3. User taps one main action.
4. The matching sub-action rail appears with only the exact list above.
5. User taps a sub-action.
6. The app verifies current exposure, geography and route ownership before
   opening its destination.
7. Active opens the exact native owner. Loading preserves the choice. Denied,
   held, stale, offline or removed returns a finished customer recovery state.
8. Chat opened from any point returns to the exact permitted origin.
9. Search, notification and deep-link entries pass through the same gate; they
   cannot bypass the visible action policy.

## Journey 3 — Workspace entry and narrowing

1. Personal user taps **Work**.
2. User taps **Workspace**.
3. If exactly one safe active workspace exists and the person previously used
   it, **Continue to [workspace name]** is the primary action.
4. If several workspaces exist, the most recently used permitted workspace is
   shown first and **All workspaces** reveals the complete status-labelled list.
5. **Add another workspace** is a separate action; it never replaces or
   duplicates an existing workspace.
6. A person with no workspace sees two understandable groupings:
   - **Earn with MoolSocial**; and
   - **Run a business or professional workspace**.
7. These groupings narrow presentation only. They are not workspace types and
   grant no permission.
8. The app requests the active, published type list. There is no hard-coded
   customer enum and no free-text user-created type.
9. A family appears only if it contains at least one currently publishable
   exact type for the person and geography.
10. User taps a family, then one exact type.
11. Back restores the prior family and scroll position; cancel returns to the
    existing Personal-user context.

## Journey 4 — exact preview, details and request

1. User taps one exact published workspace type.
2. The first view gives a concise, attractive and truthful benefit preview,
   owning MoolSocial action and service area.
3. User taps **See full details**.
4. Full details show:
   - exact work/business purpose;
   - allowed capabilities and explicit exclusions;
   - current geography/category boundary;
   - eligibility, identity, licence, vehicle, skill or document requirements;
   - applicable plan, subscription, transaction charge or no-charge fact;
   - verification and expected decision steps;
   - data/permission use;
   - support, suspension and appeal route; and
   - effective version/date.
5. User taps **Create workspace** only when the later registry/creation owner
   reports a valid request path.
6. User confirms the exact type and terms version.
7. One idempotent server request is submitted.
8. Success means **Request submitted** or another exact server state; it never
   means capability approved.
9. Pending workspace appears in **All workspaces** with reason, expected next
   step and support route.
10. Retry, Back, refresh or process death restores the same request identity.
