The launch vertical slice is one bounded verified retailer-onboarding output.
The worker never pays to apply, train, accept or receive payout. Application,
travel, time spent and unverified proof do not create payable money. Only an
approved funded output enters the payable ledger.

An approved assignment may allocate one bounded funded capacity seat to one
worker attempt. That is not the inventory reservation system excluded from the
Buy journey. It does not hold consumer stock. It prevents the same funded work
unit and its funding from being promised simultaneously to multiple workers,
and it begins only after authoritative assignment acceptance.

## Work audience and visibility model

**Normal user** means a signed-in personal-account user who has not yet created
the required Work workspace. A normal user may discover an Admin-approved
public teaser but cannot Apply or accept work.

**Target user** means a user whose verified Work profile and consented work
area match the opportunity's governed audience policy. Targeting uses Work
type, skill/training, geography, proof capability, trust and conflict rules. It
cannot use sensitive traits, contacts, other apps, personal messages or
unrelated phone activity.

| User/audience | Illustrative MVP Work, not a fixed type list | Geographic publishing | Minimum state before Apply |
| --- | --- | --- | --- |
| Normal personal user | Public previews of selected funded opportunities; no execution yet | Admin may show national, state, district or locality-relevant teasers | Create or reuse the required free Work workspace; then review full terms |
| General verified Freelancer Work | Retailer onboarding, catalogue/price/stock verification, QR placement, approved demand collection or field survey | Locality/zone, district, state, national or remote as the task allows | Exact profile, consent, area, proof capability and any required training verified |
| Specialist Onboarding/Verifier Work | Higher-trust identity, activation or structured verification outputs | Usually locality, district or state | Specialist capability, training, proof and conflict checks |
| Creator Work | Original content, editing packs and funded campaign deliverables | State, national or remote | Creator profile plus rights/disclosure and task capability |
| Delivery Partner Work | Bounded delivery route/block work | Zone, locality or district | Separately verified Delivery Partner profile; passenger Captain work remains separate |
| Verified retailer/business participant | Approved business-activation or in-store campaign output when conflict policy permits | Locality, district, state or campaign-specific | Matching business workspace plus separate Work eligibility where the participant earns |
| Manufacturer/brand/verified issuer | Creates and funds governed opportunities; not automatically a worker | Chooses only approved audience/geography scope | Verified issuer authority, funding and Admin governance approval |

The examples above are initial launch examples only. They are not a hard-coded
Work Type enum.

### Admin-created Work Type registry

Admin owns an extensible **Work Types** registry:

1. Admin taps **Create New Work Type**.
2. Admin names and describes the new work nature without selecting a mandatory
   pre-existing family.
3. Admin composes its behavior from governed primitives: compatible Work
   workspace capabilities, remote/field mode, geography, eligibility,
   conflicts, steps/custom fields, allowed proof, payout units, terms,
   consent, safety, rights, support and recovery.
4. Admin previews the new type's teaser, full terms, application, active-work
   and proof shells.
5. Admin saves a draft and obtains any applicable compliance/governance
   approval.
6. When activated, the versioned Work Type is automatically added to the
   reusable **Work Type selection** used when posting work.
7. Admin can pause, supersede or retire it for future posts. Existing published
   work and accepted assignments retain their recorded type/version.

Admin may create another type inline from the posting screen; the system saves
and governs the type first, then returns to the post with that new active type
selected. A compatible data-defined type does not require an app release. A
type requiring a new device permission, external integration, regulated
activity or executable workflow remains held for that independent approval—it
is not silently enabled by the registry.

Admin chooses one visibility mode per published version:

1. **All-user public teaser** — visible to every normal user, while clearly
   showing where the work can actually be performed.
2. **Geographic public teaser** — visible to normal users in the selected
   locality/district/state/national scope.
3. **Targeted teaser** — visible only to matching governed Work user types and
   geography.
4. **Workspace full terms** — available after the user creates or reuses the
   required Work workspace and always before **Apply**.

The public/targeted preview can be catchy and visually tempting, but it must be
truthful. It shows the verified issuer, funded status, recognizable work
nature, geography, payout amount/range and unit, closing time/capacity and
**eligibility applies**. It cannot use an inflated income promise, conceal a
worker fee or imply that preview visibility means eligibility.

After workspace creation, the full decision screen shows exact scope, output,
eligibility, work area, capacity, payout calculation and maximum, payment
timing, deadline, proof, resources/cost responsibility, consent/safety,
rights/confidentiality, correction/rejection/appeal, cancellation and terms
version. Workspace creation unlocks this detail; required verification may
still keep **Apply** disabled until the user qualifies.

## Initial launch policy and Admin ownership

Every timing and decision policy is server-owned, versioned, effective-dated,
audited and snapshotted into the opportunity and accepted assignment. An Admin
edit affects future opportunities or assignments only.

For the first retailer-onboarding slice, the accepted references demonstrate:

- a four-hour approved-assignment start window;
- one exact work deadline visible after acceptance;
- four task-specific proof items;
- an outcome-review target of no more than 24 hours;
- one correction where the opportunity terms permit it; and
- payout release within three working days after final approval.

Those values are the first launch template, not uncontrolled global constants.
Admin may later edit application close, approved-assignment start window, work
deadline, proof-review SLA, rework attempts/window, appeal SLA and payout
release target inside separately approved policy limits. Existing accepted
assignments retain their snapshot.

Before publication, Admin may repeatedly edit the work nature, title/preview,
full terms, scope, audience types, geography, capacity, payout, proof,
deadlines, review and recovery. Admin must preview the normal-user card, every
targeted-user card and the full post-workspace terms before approval.

After publication, a material edit creates a new terms/version record. Saved or
applied users must review changed material terms before proceeding; accepted
assignments remain on their original snapshot. Admin may schedule, pause,
close or replace future capacity but cannot silently rewrite active work.

Operational learning may use only consented MoolSocial Work events such as
application volume, assignment-start latency, decline/expiry, completion,
review latency, rework, appeal and payout reconciliation. It may recommend an
explained policy revision to Admin. It cannot read unrelated phone activity or
change Production by itself.
