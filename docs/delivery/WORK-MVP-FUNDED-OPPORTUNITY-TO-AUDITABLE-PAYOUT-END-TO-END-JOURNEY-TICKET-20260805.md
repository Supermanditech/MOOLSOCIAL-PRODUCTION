## Parent outcome

An eligible user can find one genuinely funded Work opportunity, understand
the exact output and payout before applying, accept one assignment once,
complete only the defined task, submit task-specific proof, receive an
explainable approval/rework/rejection decision, use an independent appeal
where permitted and reach an auditable payable, paid or accountable recovery
state.

The first launch slice is one verified retailer-onboarding output. The 45
production-grade portfolio tickets are bounded child execution units of this
complete parent acceptance ticket.

## MVP classification and reason

Classification: `mvp_required`.

The authoritative 45-day go-live plan assigns Days 21–27 to **Work and payout**
and defines the exit as one funded task completed with an auditable payout
result. Generic service booking is not substituted for this journey because
the approved route machine marks the broad **Get It Done** screens post-MVP.

## Exact operating promise

`funded capacity -> exact terms -> eligible application -> explicit assignment
acceptance -> one bounded work output -> original proof -> reasoned decision ->
immutable payable ledger -> reconciled payout or accountable recovery`

- The worker never pays an application, training, access, equipment or payout
  fee to MoolSocial for this journey.
- Applying does not assign work and does not reserve payout for the applicant.
- A bounded funded capacity seat is allocated only after authoritative
  assignment acceptance. It protects one funding/output unit from duplicate
  assignment; it is not a consumer inventory reservation or stock hold.
- Application, travel, time spent and unverified proof are not payable events.
- Only an approved funded output creates a payable ledger entry.
- No client callback, countdown or AI response can create eligibility,
  acceptance, proof approval, rejection or payout truth.

The labels below are functional tap requirements. Exact layout and final copy
remain governed by the accepted HTML reference gate.

## Who sees which Work

There are three decision layers and multiple preview-reach modes, all chosen
by an authorized Admin for each published opportunity version:

| Layer | Who sees it | What is shown | What the user can do |
| --- | --- | --- | --- |
| Public teaser | Every normal user when Admin chooses **All users**, or normal users inside a selected public geography | Catchy but truthful title/image, verified issuer, funded badge, recognizable work nature, actual work geography, payout amount/range and unit, closing time/capacity and **eligibility applies** | Tap **See this opportunity** or **Create Work workspace**; cannot Apply yet |
| Targeted teaser | Users matching the governed Work type, skill/training and consented work-area segment | The public facts plus match reason, required Work type and key proof/deadline facts | Open or create the matching Work workspace |
| Full decision | User has created or reused the required Work workspace | Complete scope, output, eligibility, location, capacity, payout formula/maximum, payment timing, deadline, proof, supplied resources/cost responsibility, safety/consent, rights/confidentiality, correction/rejection/appeal, cancellation and terms version | Review everything, complete missing verification, then **Apply** |

Workspace creation unlocks the full terms; it does not itself grant eligibility.
If verification is incomplete, the full terms stay visible while **Apply** is
disabled with the exact missing requirement.

Illustrative launch targeting is listed below. These are examples, not a fixed
Work Type list:

- normal user: public previews only until a free Work workspace is created;
- general Freelancer Work: retailer onboarding, catalogue/price/stock checks,
  QR placement, approved demand collection and field surveys;
- specialist Onboarding/Verifier Work: higher-trust identity, activation or
  structured verification output;
- Creator Work: original content, editing and governed funded campaigns;
- Delivery Partner Work: bounded delivery route/block work, separate from
  passenger Captain work;
- verified retailer/business participant: approved business-activation or
  in-store campaign output where conflict rules permit; and
- verified manufacturer/brand/issuer: creates and funds governed work but is
  not automatically eligible to perform it.

Geography may be locality/zone, district, state, national or remote. Matching
uses the user's declared/verified or explicitly consented work area; it cannot
use hidden background location, contacts, other apps, sensitive traits,
personal messages or unrelated phone behavior.

## Journey 1 — common worker tap-to-tap journey

1. User signs in with one verified personal account.
2. User taps **Mool**, then **Work**.
3. Work opens **Opportunities** by default. The dock keeps **Opportunities**,
   **My Work**, **Earnings** and **Chat** visible.
4. A normal user sees Admin-approved public teasers either platform-wide or for
   the selected public geography; a target user also sees governed
   user-type/geography matches. Seeing a district-specific teaser nationally
   never makes an out-of-area user eligible.
5. Each teaser remains catchy but truthful: recognizable work, verified issuer,
   funded status, geography, payout basis, closing time/capacity and
   **eligibility applies**. Preview visibility never means eligibility.
6. If monthly potential appears, the worker can tap its information control to
   see the funded-capacity basis and the explicit **not salary / not guaranteed
   income** explanation.
7. The worker may tap **Best Match**, **Onboarding**, **Campaign**,
   **Verification** or an approved launch filter. Filtering cannot create
   eligibility or hide a material term.
8. The user taps one teaser or **See this opportunity**.
9. Without a matching Work workspace, a workspace gate explains the required
   Work type and offers **Create Work workspace**. No application exists yet.
10. The user creates or reuses that workspace and returns to the same
    opportunity. Required verification may still be pending.
11. **Full opportunity terms** opens before any application exists.
12. The user sees the exact paid output, location, open capacity, eligibility
   profile, payout amount/unit, proof, completion deadline, review target,
   correction allowance, rejection rules, payout timing, issuer and terms
   version.
13. The user expands **Payment and payout**, **What the publisher provides**,
    **Review, correction and rejection** and any rights/consent section needed
    for the task.
14. If required verification is incomplete, **Apply** remains disabled with the
    exact missing check while all terms remain visible.
15. When eligible, the worker taps **Apply**.
16. If an eligible verified Work profile already exists, it is reused.
17. If an exact capability is still missing, the opportunity intent is saved
    and only that controlled setup opens; no duplicate workspace or silent
    category is created.
18. The server processes one idempotent application and returns **Applied**,
    **Waitlisted**, **Approved**, **Rejected** or **Expired** with a visible
    reason and next action.
19. The worker opens **My Work** or **Applications** to restore that same
    application after Back, app close, phone restart or network recovery.
20. If waitlisted, the worker sees that no assignment or payout is reserved.
21. If rejected or ineligible, the worker sees the exact failed eligibility
    requirement and any allowed correction/review route.
22. If approved, the worker taps **Open Assignment**.
23. Before acceptance, the assignment sheet shows the same terms version,
    exact output, payout, proof, deadline, approved-assignment start window,
    funding/capacity status and conflict result.
24. The worker taps **Start Work** to accept, or **Decline / Release** if the
    task cannot be performed. The final visible decline control is part of the
    reference batch because the approved examples do not yet show it fully.
25. **Start Work** succeeds only after server checks current eligibility,
    terms version, funding, capacity, conflict and expiry and records one
    idempotent acceptance.
26. On success, one funded capacity seat binds to that worker attempt and
    **Active Work** opens. On conflict or expiry, no work is created and the
    worker receives an explicit result.
27. Active Work shows one output, ordered steps, remaining time, payout,
    required proof, review target, consent/safety limits and **Support**.
28. The worker completes each exact step; progress is saved against the same
    authoritative work ID.
29. The worker taps **Continue Proof**.
30. **Submit Outcome** shows each required proof item and whether it is missing,
    captured or invalid.
31. The worker reviews the proof summary and taps **Submit for Verification**.
32. The server creates one outcome case; repeated taps or resumed uploads do
    not create duplicate cases or payout.
33. The worker sees **Verifying** and the snapshotted review target, then may
    tap **Track Earnings** or return to **My Work**.
34. If approved, the exact work ID and amount move from held to payable in the
    immutable ledger.
35. If rework is permitted, the worker sees the exact failed requirement,
    retained valid proof, remaining attempt and deadline, taps **Start
    Rework**, corrects only that requirement and resubmits.
36. If rejected, the worker sees the evidence considered, reason, rule version,
    reputation effect and **Appeal** where policy permits it.
37. In **Earnings**, the worker sees **Held**, **Payable**, **Processing**,
    **Paid**, **Failed** or **Reversed** separately, with the masked verified
    destination.
38. The worker opens a ledger row to see the work, proof decision, adjustment,
    payout reference and support/appeal linkage.
39. Every nonterminal or failed state offers **Chat**, **Support** or the exact
    next recovery action without asking the worker to apply or submit again.

## Journey 3 — application, assignment and next-worker recovery

1. **Apply** stores the opportunity ID and terms version before routing to any
   missing setup.
2. Server eligibility checks identity, profile, skill/training, geography,
   proof capability, safety/trust, conflicts, funding and remaining capacity.
3. An application never allocates a funded seat and never creates payable
   money.
4. Selection returns a bounded assignment offer with an explicit start-by
   time. The first launch reference demonstrates a four-hour start window.
5. The offer is notified in-app and in MoolChat. Live external notifications
   are outside this ticket unless separately approved.
6. The worker opens the assignment and sees the exact immutable terms snapshot.
7. **Start Work** is an explicit authoritative acceptance, not a navigation
   event.
8. A valid acceptance atomically consumes one available funded output capacity
   unit and creates one active work identity.
9. A duplicate tap returns the original accepted result.
10. If the worker taps **Decline / Release**, the offer closes immediately and
    the reason may be collected only from an approved, minimal list.
11. If the start window expires, late acceptance is rejected and no active work
    appears.
12. Decline or expiry releases the capacity and may offer the unchanged task to
    the next server-eligible worker.
13. Reassignment cannot reduce payout, shorten the already published work
    deadline unfairly, alter proof or hide changed terms. A material change
    creates a new terms version and a fresh decision.
14. Funding/capacity exhaustion, opportunity close or eligible-candidate
    exhaustion ends the assignment path explicitly.

## Journey 4 — active work, consent and field safety

1. Worker opens **My Work** and taps the active assignment.
2. The header shows work ID, exact output, place, remaining time and current
   authoritative state.
3. The worker sees only the steps required for that bounded output. For the
   launch retailer-onboarding slice these are: meet the authorized owner,
   capture approved business details, place/verify the QR and complete the
   first activation.
4. Owner identity/OTP, business consent and task prerequisites are verified at
   the step that needs them.
5. The worker is told not to collect cash, passwords or unrelated documents.
6. Camera, location, OTP or document permission is requested just in time with
   an explanation and an allowed denial/recovery path.
7. Offline-safe local progress remains pending until server reconciliation; it
   cannot fabricate completion, identity or proof approval.
8. If the business is unavailable, the worker taps **Support** then
   **Business unavailable** and receives the allowed reschedule, release or
   reassignment result.
9. If location is wrong, the worker taps **Wrong location** and submits the
   minimum evidence needed for correction.
10. For a safety issue, the worker taps **Safety issue**; priority support may
    pause or release the task without requiring completion.
11. For a terms question, the worker taps **Terms question / Chat** while the
    same terms snapshot remains visible.
12. Deadline expiry, funder cancellation or worker release records actor,
    reason and evidence and closes or recovers the task exactly once.

## Journey 5 — proof capture and outcome submission

1. Worker taps **Continue Proof** from the active work.
2. The screen lists only the proof required by the accepted terms. For the
   launch slice this can include owner OTP, shop photo with approved
   GPS/timestamp, QR scan activation and owner confirmation.
3. Each proof control shows why it is needed, its permission state and its
   captured/invalid/missing result.
4. Original media or document evidence is preserved; display derivatives never
   replace the original record.
5. Integrity metadata binds evidence to worker, work, step, time, permitted
   place/device signal and consent record as applicable.
6. The user can replace a failed capture before submission without duplicating
   the outcome.
7. The summary shows **4 of 4 captured** or the exact missing requirement,
   amount held and expected review target.
8. Worker taps **Submit for Verification**.
9. The server validates work ownership, active state, deadline/recovery policy,
   evidence completeness, integrity and idempotency before creating one case.
10. Submission changes to **Verifying**. It does not approve output or release
    money directly.
11. Deterministic integrity checks may clear normal cases; ambiguous or adverse
    exceptions route to an authorized reviewer.

## Journey 6 — review, rework, rejection and independent appeal

### Reviewer decision

1. Authorized reviewer opens the proof queue and selects the exact work case.
2. Reviewer sees the accepted terms/rule version, original proof and integrity
   results, but no unrelated worker data.
3. Reviewer taps **Approve outcome**, **Request rework** or **Reject**.
4. Approval records the decision once and emits the payable event.
5. Rework requires one exact failed criterion, preserved valid proof, allowed
   attempt count and deadline from the snapshotted terms.
6. Rejection requires a specific reason, evidence references, policy version,
   worker-visible consequence and appeal availability.

### Worker rework

1. Worker opens **History & Support**, then **Issues**.
2. Worker taps the affected rework row.
3. The sheet shows the exact correction and **Start Rework**.
4. Only invalid or missing proof reopens; valid proof remains attached.
5. Worker corrects and taps **Resubmit** once.
6. If no rework was promised, no new requirement is invented after completion.

### Worker appeal

1. Worker opens the rejected work record and taps **Appeal**.
2. Worker reviews the original evidence, reason and rule and may add permitted
   new evidence or a concise explanation.
3. Worker taps **Submit Appeal** once.
4. An independent reviewer who did not make the first adverse decision is
   assigned.
5. Appeal may uphold, revise or overturn the decision with a new reason.
6. Overturn creates or restores the correct payable/reputation result through
   append-only events; history is never silently rewritten.
7. One disputed task cannot silently destroy all future eligibility.

## Journey 7 — earnings and payout

1. Worker taps **Earnings**.
2. The summary separates **Available for payout**, **Under review** and
   **Paid**; potential and application counts never appear as earned money.
3. Worker sees the masked verified payout destination and next approved payout
   target.
4. Each ledger row names the work ID, approved/held outcome and amount.
5. Approval creates one **Payable** entry only when authoritative funding and
   the exact decision are valid.
6. Payout service moves the entry to **Processing** using one idempotent
   instruction and immutable destination snapshot.
7. Authoritative provider reconciliation creates **Paid**, **Failed** or
   **Reversed**. A client callback cannot create paid status.
8. Unknown status stays processing/reconciling and cannot cause another payout.
9. **Paid** exposes an approved bank/provider reference such as UTR and date.
10. **Failed** offers **Fix payout destination** or **Get help** without
    deleting the payable amount.
11. Worker taps the statement control, reviews task-linked held/payable/paid
    values and taps **Prepare Statement** for the approved export.
12. Payout timing uses the policy snapshot; later Admin changes do not rewrite
    an accepted assignment or already-payable entry.

### Reviewer

1. Authorized reviewer taps **Proof review** and opens a due case.
2. Reviewer sees only decision-relevant worker/work/terms/evidence data.
3. Reviewer records **Approve outcome**, **Request rework** or **Reject with
   reason**.
4. Self-review, issuer conflict or prior appeal involvement blocks the action
   and routes another reviewer.
5. Decision becomes visible to worker, funder, Admin audit and ledger through
   one authoritative event.

## Journey 9 — failure, cancellation and support recovery

| Failure | Worker sees | Accountable next action |
| --- | --- | --- |
| Public teaser does not match user type/geography | Teaser may remain public but **Apply eligibility required** | Create/reuse Work workspace; server evaluates the governed target policy. |
| Targeted opportunity is outside declared/consented area | **Not available in your work area** | Change the declared work area through the approved profile route or choose another opportunity; no hidden tracking. |
| Terms changed after Save/Apply but before acceptance | **Terms changed — review again** with before/after material facts | Explicitly consent to the new version or withdraw; no silent continuation. |
| Admin edits after assignment acceptance | Original accepted terms remain visible | New version affects only permitted future capacity; recover active work under its snapshot. |
| Opportunity stale or funding exhausted before Apply | **No longer available** with reason | Return to current Opportunities; no application created. |
| Duplicate/unknown Apply | **Checking your application** | Reconcile original command; never create another application. |
| Eligibility missing | Exact failed check | Open only permitted profile correction or choose another opportunity. |
| Approved offer expired | **Assignment expired** | Release seat; optionally offer unchanged work to next eligible worker. |
| Duplicate/late Start Work | Original active work or explicit expiry/conflict | Never create a second active work record. |
| Business unavailable or wrong location | Paused/support-linked work | Reschedule, release, correct or reassign under policy. |
| Safety risk | **Work paused for safety** | Priority support; no completion pressure. |
| Upload interruption | **Proof pending upload** | Resume original evidence upload and case identity. |
| Proof integrity conflict | Exact flagged requirement | Human exception review; no automatic rejection/payout. |
| Review SLA missed | **Review delayed** with support owner | Escalate reviewer queue; funding remains held and visible. |
| Rework not possible before deadline | Exact expiry/review route | Support or appeal under snapshot; no hidden rejection. |
| Rejection disputed | **Appeal available** where permitted | Independent review with original evidence/rule. |
| Payout status unknown | **Processing / reconciling** | Poll/reconcile provider; never send duplicate payout. |
| Payout failed | Amount remains payable/failed | Correct verified destination or open payout support. |
| Funder cancellation | Actor, reason and affected scope visible | Stop future capacity; handle accepted work/funding under snapshot. |

The support case always links the same opportunity, assignment/work, terms,
proof, decision and payout identities. Support cannot overwrite authoritative
history or promise money outside approved finance policy.

## Terminal outcomes

The parent journey is terminal only in one of these explicit states:

- opportunity closed/unavailable before application;
- application rejected, expired or withdrawn with reason;
- assignment declined/expired/released without active work;
- active work completed and outcome approved, then payable/paid;
- rework completed and finally approved/rejected;
- rejection/appeal finally resolved with reason;
- task cancelled/expired with funding/capacity recovery recorded; or
- payout remains failed/reversed with one accountable support/reconciliation
  owner and the worker's ledger truth preserved.

“Guaranteed payout” is not promised for unapproved work. The guaranteed
platform behavior is exact terms before commitment, bounded and recoverable
states, no worker fee, reasoned decisions, immutable money history and an
accountable terminal outcome.
